# 中文分词设计

本项目相对 Rust 原版的核心增量。原版 tantivy 默认 `en_stem` 分词器依赖空格词界，对中文（连续书写、无分隔符）完全失效——整段汉字成为一个 token，查询「注意力」无法命中「注意力机制」。

## 设计目标

1. 中英混写内容开箱即检（单二进制，无外部词典文件）
2. 索引与查询分词严格同源
3. 纯英文/纯拉丁内容零额外成本（不加载词典）
4. 可预见的内存与延迟预算

## 分词器模式

配置键：`[index] tokenizer`。

| 值 | 行为 | 词典 | 典型场景 |
|---|---|---|---|
| `auto`（默认） | 汉文 run 走 gse，其余走拉丁词分词；**懒加载**（首次遇到汉字才加载） | 内嵌 | 中英混写（绝大多数） |
| `gse` / `zh` / `cjk` / `jieba` | 同 auto，构造时即加载词典（尽早暴露词典问题） | 内嵌 | 纯中文库 |
| `simple` / `en` / `en_stem` | 汉字退化为单字 unigram；拉丁按字母数字 run | 无 | 纯英文库 / 内存受限 |

`en_stem` 是原版默认值，作为兼容别名保留（映射到 `simple`；Go 版不实现词干化——BM25 下收益有限，见 parity.md）。

## 处理管线

```
text
  │
  ▼ splitRuns：按 Unicode 脚本切 run（Han vs 其余）
  ├─ Han run ──▶ gse.CutSearch(s, hmm=true)      搜索模式：全词 + 子词
  │                 │
  │                 ▼ 过滤纯标点/符号 token；ToLower
  └─ 其余 run ──▶ latinWords：字母/数字连续段，ToLower；其余字符为分隔
  │
  ▼ 合并输出（保留重复——BM25 需要词频）
```

### 为什么用 CutSearch（全词+子词）而非精确模式

搜索模式同时输出全词与子词，是 CJK 检索的标准召回策略（对应 Lucene CJKAnalyzer 的 bigram 思路）：

```
CutSearch("服务器集群容错") → [服务 器 服务器 集群 容错]
```

查询「容错」「服务器」都能命中。精确模式只出全词，查询子串即脱靶。代价是索引 token 数量增约 1.5–2×，在个人 wiki 规模（万页级）无感。

### 脚本路由示例

```
"混合文本BM25检索与注意力机制"
→ 汉文段「混合文本」→ [混合 文本]
→ 拉丁段「BM25」   → [bm25]
→ 汉文段「检索与注意力机制」→ [检索 与 注意 注意力 机制]
```

拉丁词不受词典污染（gse 自带的英文切分被绕开），汉文不受空格语义影响。

## 词典

- **来源**：jieba 词频词典（`dict/zh/s_1.txt`，352,279 词条，4.9MB），经 [go-ego/gse](https://github.com/go-ego/gse)（Apache-2.0）的 `LoadDictStr` 格式加载。
- **嵌入方式**：`go:embed` 进 `internal/assets`，编译期进二进制。**不走 gse 的 `LoadDictEmbed`**——它的 switch 会把日文字典（23MB）等全部常量链进二进制（实测 34MB）；手动嵌入只带 zh_s，实测二进制 20MB / strip 15MB。
- **更换/扩充词典**：替换 `internal/assets/dict/zh_s.txt`（gse 文本格式：`词 词频 [词性]`，每行一条）后重新编译。自定义领域术语直接追加行即可。

## 成本模型（M1 实测）

| 项 | 数值 |
|---|---|
| 词典加载（一次） | ~400ms，~100MB RSS |
| 分词吞吐 | ~42µs/百字短文（`BenchmarkTokenizeChinese`） |
| 1000 页中文库全量重建 | 188ms（含分词） |
| 懒加载收益 | 纯拉丁内容 0 加载 |

**推论**：CLI 单发命令每进程都付 400ms 词典成本；常驻服务（MCP/ACP）只付一次。这是词典型分词器的固有代价，不做词典二进制缓存（gse 的 cedar trie 不可直接序列化，收益/复杂度比不划算）。

## 与 BM25 的衔接

- 索引侧：`BuildIndexDoc` 把 title×3 / summary×2 / body×1 的 token 合并成加权词袋（见 search.md）。
- 查询侧：同一 `Tokenizer.Tokens(query)`，多词按 OR 命中、得分求和（近似原版 tantivy 的多字段 QueryParser）。
- **同源约束**：索引记录 `TokenizerName`；`Open()` 发现与当前配置不符即弃用持久化索引强制重建。改分词器配置后首次操作自动全量重建，无需手工干预。

## 已知限制

- 无停用词表：「的/了」等高频词 idf≈0，对 BM25 排序无实际影响，不做（可测量出问题再加）。
- 无词干化（拉丁）：`en_stem` 别名不含 stemming。
- 繁体：词典为简体（zh_s）；繁体内容会退化为较多的子词/单字命中，仍可检索。
- `[[slug|alias]]` 管道别名与原版一致不支持。
